Fecha: 2026-05-29

Resumen
-------
Este documento mapea las funcionalidades clave del sistema frente a los controladores y servicios implementados en el código fuente, identifica código potencialmente muerto y brechas entre capas, y propone las 3 prioridades siguientes para consolidar el MVP.

Dead code / código posiblemente no utilizado
------------------------------------------
- `EnrollmentService.mapStudentsView(List<User>)` — definido en `EnrollmentService` pero no referenciado desde controladores (buscar usages: none). Posible candidato a eliminar o reutilizar.
- `EnrollmentService.getCourseClassesFilterView()` — definido pero no encontrado en referencias fuera del propio servicio.
- `EnrollmentService.getSubjectsWhereTeacherIsTitularView(Long)` — definido pero no referenciado externamente.
- `controllers/EnrollmentControllerVIEJO.java` — controlador histórico/legacy presente en el proyecto; verificar si su registro/uso sigue vigente. Si no, mover a carpeta `legacy/` o eliminar.

Brechas detectadas (conexión entre capas)
---------------------------------------
- Endpoint `POST /student/enroll` (en `EnrollmentStudentController`) valida correlativas pero no completa la inscripción ni devuelve un flujo claro — parece incompleto o duplicado del endpoint `/student/inscripciones/confirmar`. Riesgo: UX rota y puntos muertos.
- `SecurityController` incluye `/dashboard` y `/logout` en la lista pública en `before("/*")` — esto puede permitir accesos no deseados si la lógica de redirección no protege correctamente rutas internas.
- Algunos métodos utilitarios en `EnrollmentService` (mapear vistas, filtros) no se usan; si se pretende usarlos desde vistas JS/REST, deben exponerse o limpiarse.
- Validación de roles/roles por ID: el `AuthController` fuerza `role = 1` en un endpoint público, lo cual es peligroso. Hay inconsistencias en cómo se asigna/espera el `role_id` (nombres `ADMIN`, `TEACHER`, `STUDENT` vs IDs numéricos). Recomiendo estandarizar constantes/enums.

Próximas 3 prioridades para consolidar el MVP
-------------------------------------------
1) Corregir y unificar el flujo de inscripción de estudiantes (Alta prioridad)
	- Eliminar o arreglar `POST /student/enroll` (completar la lógica) y asegurarse que la ruta de confirmación invoca siempre `EnrollmentService.enrollStudent` y maneja errores transaccionalmente.
	- Añadir validación atómica de cupos (ya existe parcialmente) y bloquear race conditions (bloqueo DB o verificación/reintento en transacción).

2) Quitar/archivar código muerto y documentar contratos de servicio (Media prioridad)
	- Mover `EnrollmentControllerVIEJO` a `legacy/` o eliminar si no se usa. Eliminar esto...
	- Remover métodos no referenciados en `EnrollmentService` o documentar su uso previsto.
	- Añadir comentarios Javadoc y un README técnico corto listando responsabilidades de cada servicio.

3) Seguridad y consistencia de roles / pruebas (Alta prioridad)
	- Revisar `SecurityController` para reducir la lista blanca y aplicar checks finos por ruta.
	- Arreglar la asignación de roles (no forzar `role = 1` en un endpoint público). Introducir constantes/enum para roles y usarlas en los filtros.
	- Añadir pruebas unitarias básicas para `AuthService` y `EnrollmentService` (tests de validación, hashing, inscripción con cupo lleno). Esto ayudará a prevenir regresiones.

Notas finales y recomendaciones rápidas
-------------------------------------
- Agregar scripts de inicialización de la BD (`src/main/resources/schema.sql` ya existe; incluir datos de prueba en `db/` o `resources/data/seed.sql`).
- Considerar introducir inyección de dependencias ligera (constructor injection) para servicios, facilitando mocks en tests.
- Añadir una tarea de limpieza/format (maven/spotless) y un pipeline CI + job `mvn test`.

Si querés, implemento las correcciones prioritarias: 1) cerrar el endpoint incompleto de inscripciones y unificar el flujo; 2) mover/eliminar `EnrollmentControllerVIEJO`; 3) cambiar la validación de roles y añadir constantes. ¿Cuál querés que haga primero?
